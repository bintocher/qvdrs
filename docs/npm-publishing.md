# Публикация npm

Пакет `qvdrs` использует пять платформенных пакетов с нативными модулями.
Версия основного пакета, всех платформенных пакетов и optionalDependencies
должна совпадать. Текущий выпуск - `0.7.2`.

| Пакет | Платформа |
|---|---|
| `qvdrs` | Основной пакет |
| `@bintocher/qvdrs-win32-x64-msvc` | Windows `x64` |
| `qvdrs-linux-x64-gnu` | Linux `x64` |
| `qvdrs-linux-arm64-gnu` | Linux ARM64 |
| `qvdrs-darwin-x64` | macOS Intel |
| `qvdrs-darwin-arm64` | macOS Apple Silicon |

## Доступ GitHub Actions

Каждому существующему пакету нужна отдельная связь Trusted Publishing:

| Поле | Значение |
|---|---|
| Provider | GitHub Actions |
| Organization or user | `bintocher` |
| Repository | `qvdrs` |
| Workflow filename | `release-npm.yml` |
| Environment | Пустое значение |
| Разрешение | Прямая публикация `npm publish` |

Workflow работает на GitHub-hosted runners и использует `id-token: write`.
Сохраненный npm-токен для этого не нужен. После создания новой связи первый
успешный выпуск через нее должен пройти в течение двух суток.

Документация: https://docs.npmjs.com/trusted-publishers/.

## Первый выпуск нового пакета

Trusted Publishing настраивается для уже существующего пакета. С 2026-10-02
npm поддерживает создание нового пакета через предварительную публикацию,
после которой доступны его настройки и Trusted Publishing. Обычная первая
публикация также возможна, но требует подтверждения владельца и не проверяет
доступ GitHub Actions. Вход в npm на сайте сам по себе не авторизует командную
строку. Браузер автоматически открывать не нужно:

```text
npm login --auth-type=web --browser=false
npm whoami
npm publish --access public --browser=false
```

Первый выпуск Windows-пакета должен содержать настоящий файл
`qvdrs.win32-x64-msvc.node` и описание версии `0.7.2`.
Использовать модуль из сборки соответствующего исходного кода.
При обычной первой публикации после нее настроить связь с GitHub.

Проверено 2026-11-17: npm отклонил имя `qvdrs-win32-x64-msvc` с ошибкой
`Package name triggered spam detection`. Имя в собственном пространстве
`@bintocher/qvdrs-win32-x64-msvc` принято реестром при предварительной публикации.
Поэтому Windows-загрузчик и optionalDependencies используют scoped-имя.

Предварительная публикация через `npm stage publish` создает служебную запись
`0.0.0-stage`, а сама версия до подтверждения недоступна пользователям.
При снятии единственной предварительной версии в проверке 2026-11-17 исчезла
запись нового пакета вместе с созданной связью Trusted Publishing.
Поэтому нельзя удалять единственную предварительную версию до появления
настоящей опубликованной версии.

Для выпуска Windows-пакета `0.7.2` через OIDC использован следующий порядок.
Создание, настройка связи, настоящий выпуск и очистка проверены 2026-11-17.
Начинать в присутствии владельца, поскольку настройки и последующая очистка
требуют личного подтверждения:

1. В отдельной копии настоящего Windows-пакета задать версию
   `0.7.2-bootstrap.0`. Версии в основном репозитории оставить `0.7.2`.
2. Выполнить `npm stage publish --tag bootstrap --access public --browser=false`.
   Сохранить stage ID. Не подтверждать и не снимать эту предварительную версию.
3. Создать и прочитать обратно связь Trusted Publishing для
   `@bintocher/qvdrs-win32-x64-msvc` с указанными выше полями.
4. Запустить `Publish to npm` из `main`. Предварительная версия занимает только
   свой номер; документация npm разрешает публикацию других версий, пока она
   ожидает решения. Поэтому настоящий выпуск `0.7.2` использует свободный номер.
5. Проверить настоящий выпуск `0.7.2` и доступ GitHub Actions. Затем снять
   только предварительную `0.7.2-bootstrap.0` через `npm stage reject <stage-id>`
   и повторно проверить существование пакета и связи.

Предварительная `0.7.2-bootstrap.0` не является выпущенной версией библиотеки.
Срок ее хранения в рассмотренной документации не указан.

Официальное объявление новой возможности:
https://github.blog/changelog/2026-10-02-npm-staged-publishing-now-supports-creating-new-packages/.

Документация: https://docs.npmjs.com/cli/v11/commands/npm-trust/#prerequisites
и https://docs.npmjs.com/staged-publishing/.

## Запуск выпуска

Обычный push коммита или тега не запускает публикацию. Общий выпуск запускается
при публикации GitHub Release. Для отдельного повторного выпуска npm запустить
`Publish to npm` вручную из нужной ветки.

Для `0.7.2` использовать `main`: тег `v0.7.2` создан до исправления исполнителей
macOS и Windows-зависимости. Новый тег и повышение версии для этого не нужны.

Перед общим следующим выпуском обновить Cargo.toml, Cargo.lock, pyproject.toml,
package.json, package-lock.json, пять npm/*/package.json и optionalDependencies.
GitHub Release также запускает публикации Python и Rust.

При повторном запуске уже опубликованные платформенные версии нужно проверить
и пропустить. Ошибки доступа или сети не означают отсутствия версии.
Основной пакет публиковать после всех платформенных пакетов.

После выпуска проверить наличие всех шести версий в реестре, затем установить
`qvdrs@0.7.2` в пустой каталог и проверить загрузку нативного модуля.

Документация: https://docs.npmjs.com/cli/v11/commands/npm-publish/
и https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository.

## Состояние выпуска на 2026-11-17

Через GitHub Actions выпущены все шесть пакетов `0.7.2`, перечисленные выше.
Для каждого `latest` указывает на `0.7.2`. Архивы скачаны из npm, контрольные
суммы SHA-512 совпадают с метаданными. У всех шести версий есть provenance.
Обычная команда `npm install qvdrs@0.7.2` с пустым npm-кешем прошла в чистой
LXC. Linux-модуль загрузился и прошел проверку поиска значений.

Успешный прогон: https://github.com/bintocher/qvdrs/actions/runs/44060370308.
Проверки CI этого исходного кода прошли. Сценарий публикации проверен
11 проверками в LXC и на реальных метаданных npm 12. В workflow закреплен
npm 12.2.2. Ответ `npm view --json` принимается как объект npm 11 или
массив из одного элемента npm 12; неоднозначный ответ блокирует публикацию.

Предварительная `0.7.2-bootstrap.0` снята с личным подтверждением владельца.
Список stage пуст. Настоящая версия `0.7.2`, метка `latest` и та же связь
Trusted Publishing после очистки прочитаны и подтверждены.

При проверке нового выпуска npm временно возвращал старый 404 для обычного
адреса архива с `Cache-Control: public, max-age=300`. Архив по свежему адресу
уже был доступен и совпадал по SHA-512. После обновления ответа сервера прошла
обычная установка с пустым кешем. Не менять версию и не повторять публикацию
из-за такого временного ответа: сначала проверить метаданные и возраст ответа.
